## OAuth

인터넷 사용자들이 비밀번호를 제공하지 않고 다른 웹사이트상의 자신들의 정보에 대해 웹사이트나 어플리케이션의 접근 권한을 부여할 수 있는 공통적인 수단으로서 사용되는, 접근 위임을 위한 개방형 표준

OAuth 2.0은 1.0에서 알려진 보안 문제를 개선한 버전

## OAuth의 구성 요소

- Resource Owner: 웹 서비스를 이용하려는 유저, 자원을 소유하는 자, 사용자
- Client: 애플리케이션 서버
- Authorization Server: 권한을 부여해주는 서버, 사용자는 이 서버로 ID, PW를 넘겨 Authorization Code를 발급받고, Client는 이 서버로 Authorization Code를 넘겨 Token을 발급받음
- Resource Server: 사용자의 개인정보를 가지고있는 애플리케이션 (구글 등) 서버
- Access Token: 자원 접근 권한을 Resource Owner가 인가하였음을 나타내는 자격 증명
- Refresh Token: Access Token을 재발급받게 해줌

# JWT

서버가 클라이언트 인증을 확인하는 방법은 대표적을 3가지의 큰 방식이 있음

쿠키, 세션, 토큰

### Cookie 인증

Key-value 형식의 문자열 덩어리

클라이언트가 어떤 웹사이트를 방문할 경우, 그 사이트가 사용하고 있는 서버를 통해 클라이언트의 브라우저에 설치되는 작은 기록 정보 파일

클라이언트가 서버에 요청을 보냄 → 서버는 요청에 대한 응답을 작성할 때, 저장하고 싶은 정보를 응답 헤더의 Set-Cookie에 담음 → 이후 해당 클라이언트는 요청을 보낼 때마다, 매번 저장된 쿠키를 요청 헤더의 Cookie에 담아 보냄

<aside>
💡

### 단점

- 보안에 취약하다 - 쿠키의 값을 그대로 보냄
- 용량 제한이 있다 - 큰 정보 담을 수 없음
- 브라우저간 공유가 불가능하다 - 웹브라우저마다 쿠키에 대한 지원 형태가 다름
- 네트워크의 부하가 심해진다 - 쿠키의 사이즈가 커질수록 네트워크의 부하가 심해짐
</aside>

### Session 인증

쿠키의 보안적 이슈 때문에 세션은 비밀번호 등 클라이언트의 민감한 인증 정보를 브라우저가 아닌 서버 측에 저장하고 관리

서버의 메모리에 저장하기도 하고, 서버의 로컬 파일이나 데이터베이스에 저장하기도 함

민감한 정보는 서버에서 모두 관리

유저가 웹사이트에서 로그인하면 세션이 서버 메모리에 저장됨 → 서버에서 브라우저 쿠키에 Session ID를 저장함 → 쿠키에 정보가 담겨있기 때문에 브라우저는 해당 사이트에 대한 모든 요청에 Session ID를 쿠키에 담음 → 서버는 클라이언트의 Session ID와 서버가 가진 Session ID를 비교하여 인증 수행

<aside>
💡

### 단점

- 해커가 Session ID 자체를 탈취하여 클라이언트인 척 위장 가능
- 서버에서 세션 저장소를 사용하므로 요청이 많아지면 부하가 심해짐
</aside>

### Token 인증

클라이언트가 서버에 접속하면 서버에서 해당 클라이언트에게 인증되었다는 의미의 토큰을 부여함

토큰은 유일하며 토큰을 발급받은 클라이언트는 또 다시 서버에 요청을 보낼 때 요청 헤더에 토큰을 심어서 보냄

서버는 클라이언트에서 받은 토큰을 서비스에서 제공한 토큰과 일치 여부를 체크하여 인증 과정 처리

<aside>
💡

토큰은 세션과는 달리 서버가 아닌 클라이언트에 저장되어 서버의 부담을 덜 수 있음

→ 서버에서는 위조 여부만 판별하면 된다

</aside>

<aside>
💡

### 단점

- 토큰 자체의 데이터가 길어 인증 요청이 많아질수록 네트워크 부하가 심해짐
- PayLoad 자체는 암호화 되지 않기 때문에 중요한 정보 담을 수 없음
- 토큰을 탈취할 시 대처가 어려움 (따라서 사용기간 제한을 설정함)
</aside>

## JWT Json Web Token

인증에 필요한 정보들을 암호화시킨 JSON 토큰

JWT 기반 인증은 JWT 토큰을 HTTP 헤더에 실어 서버가 클라이언트를 식별하는 방식

JWT는 JSON 데이터를 Base64 URL-safe Encode를 통해 인코딩하여 직렬화한 것 - 토큰 내부에는 개인키를 통한 전자서명도 들어있음

### JWT 구조

.을 구분자로 세 가지 문자열의 조합

```tsx
XXXXXX.YYYYYY.ZZZZZZ
(헤더Header).(내용Payload).(서명Signature)
```

헤더에는 JWT에서 사용할 타입과 해시 알고리즘의 종류가 담겨있음

Payload는 서버에서 첨부한 사용자 권한 정보와 데이터가 담김

Signature는 전자서명이 담겨있음

### Payload

토큰에서 사용할 정보의 조각인 Claim이 담겨 있음

사용될 정보에 대한 내용을 담고 있음

```tsx
{
	userId:3,
	name:"박고은"
}
```

페이로드는 대표적으로 Registered claims, Public claims, Private Claims 세 가지로 나뉨

- Registed Claims: 미리 정의된 클레임 (ex: 발행자, 만료 시간, 제목, 발행 시간, jti)
- Public Claims: 사용자가 정의할 수 있는 클레임 (공개용 정보 전달을 위해 사용)
- Private Claims: 해당 당사자들 사이에 정보를 공유하기 위해 만들어진 사용자 지정 클레임, 외부에 공개되도 상관 없지만 해당 유저를 특정할 수 있는 정보가 담김 (userName: “Goeun”)

# Bearer Token

## Bearer Token

리소스에 접근할 수 있다는 것을 증명하는 데이터 조각으로, 보통 문자열 형태

이 토큰을 소지한 사람이라면 추가적인 증명 없이도 사용할 수 있음

앱이 매번 신원을 확인받지 않고도 API에 탑승할 수 있도록 해줌

## 실제 동작 방식

1. 사용자 로그인
    1. 은행 앱에 사용자 이름과 비밀번호로 로그인
2. 인증 서버가 토큰 발급
    1. 인증 서버가 정보 확인 후 Bearer Token 반환
3. 클라이언트가 토큰 사용
    1. 잔액 확인이나 송금 버튼을 누를 때마다 앱은 HTTP 요청에 토큰을 포함함
4. API 검증
    1. 서버는 토큰이 아직 유효한지, 만료되지 않았는지 등등을 확인
5. 접근 허용
    1. 모든 체크 통과시 서버가 요청 정보 반환

## Bearer Token vs Access Token

### Access Token : 허가증

나 이 API 써도 돼~를 증명하는 열쇠

사용자가 리소스에 접근할 수 있도록 허가하는 자격 증명

### Bearer Token: 전달 형식

이거 가지고 있으면 누구든 접근 허용

그냥 HTTP 헤더에 들고 오면 무조건 인증해줌 → 토큰 자체가 신원증명

💡

모든 Bearer Token은 Access Token임

</aside>
